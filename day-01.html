What is it?

Web development is building experiences that run in a browser

A website is files (HTML, CSS, JS, images) delivered over the internet and rendered by a browser.

Why we need it

Businesses, schools, shops, and apps all meet users through the web.

How it works

You write code → a server stores/sends it → the browser displays it.

Real world

YouTube, your university portal, and a restaurant menu site all use this model.

Frontend vs backend

Two jobs. One product.

Frontend

What the user sees

Layout, colors, buttons, forms. HTML, CSS, JavaScript, React.

Analogy: the dining room, menu, and waiter’s tray.

Backend

What happens behind the scenes

Accounts, databases, payments, emails. Servers and APIs.

Analogy: the kitchen, inventory, and recipes.

This course is frontend-first. We will still talk to backends using APIs from Day 7.

Ask: “If a ‘Pay Now’ button does nothing, is that frontend or backend?” Answer: could be either — UI might be broken, or the server might reject the payment. That’s why teams debug both sides.

What happens when we enter a URL

Request → Response → Render

  1. Browser looks up the address (DNS: name → number).
  2. Browser sends an HTTP request: “Please give me this page.”
  3. Server sends an HTTP response: HTML (then CSS, images, JS).
  4. Browser reads HTML and renders the visual page.
// Simplified conversation
You:  GET https://example.com
Server: 200 OK
<html>...the page...</html>
Live demo: open DevTools → Network, reload a simple site, click the first document. Show status 200 and the HTML. Do not go deep into DNS.

Problem → solution → technology

Why HTML exists

Problem

A browser cannot guess your heading, your photo, or your contact form. It needs a shared language for structure.

Solution

HTML — HyperText Markup Language — labels pieces of content so the browser knows what they are.

HTML is not a programming language. It is a structure language.

Analogy: HTML is the skeleton, CSS is clothing, JavaScript is muscles. Repeat this triad all course.

Introduction to HTML

Tags wrap content and give it meaning

<h1>Mahedi</h1>
<p>I am learning web development.</p>
<a href="https://github.com">My GitHub</a>

Opening tag

<p>

Content

the text inside

Closing tag

</p>

Element anatomy

Element = tag + content + (optional) attributes

<img src="me.jpg" alt="Photo of Mahedi">
  • src tells the browser which file to load.
  • alt describes the image if it cannot be seen.
  • Some elements are empty: they have no closing tag (img, br, hr, input).

Document structure

Every page starts with this skeleton

<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8">
    <title>My Profile</title>
  </head>
  <body>
    <h1>Hello</h1>
  </body>
</html>
Live type this from empty file. Save as index.html. Open in browser. Change title — show the browser tab update. That “aha” is gold.

Head vs body

<head>

Instructions for the browser: title, character set, CSS links. Users do not see this directly.

<body>

Everything visible: text, images, links, forms.

If you put an <h1> only in the head, will the user see it?

Expected answer: No. Visible content belongs in body.

Headings

Headings create outline, not decoration

<h1>Mahedi Hasan</h1>
<h2>About me</h2>
<h2>Skills</h2>
<h3>Frontend</h3>
Use one h1 per page. Do not skip levels just to make text look smaller. CSS will handle size tomorrow.

Paragraphs and text

Browsers collapse extra spaces. Tags create structure.

<p>I am a student learning HTML.</p>
<p>I like <strong>football</strong> and <em>photography</em>.</p>
<br>  <!-- line break, use sparingly -->
<hr>  <!-- thematic divider -->

Links

Hypertext means documents can connect

<a href="https://developer.mozilla.org">MDN Docs</a>
<a href="projects.html">My projects</a>
<a href="mailto:you@email.com">Email me</a>
<a href="#skills">Jump to skills</a>

Absolute URLs start with https://. Relative URLs point to files beside yours.

Common confusion: href vs the clickable text. Demo a link that says “Click here” vs a descriptive link. Accessibility preview.

Images

Always pair src with alt

<img
  src="profile.jpg"
  alt="Portrait of Mahedi smiling"
  width="240"
>

If the image fails

alt text still explains the picture to people and to search engines.

File location

If the photo is in an images folder: src="images/profile.jpg".

Lists

Use lists for groups, not for layout hacks

<ul>
  <li>HTML</li>
  <li>CSS</li>
</ul>
<ol>
  <li>Learn</li>
  <li>Practice</li>
</ol>

ul = unordered (bullets). ol = ordered (numbers). Nested lists are allowed.

Tables

Tables are for tabular data — not page layout

<table>
  <tr><th>Skill</th><th>Level</th></tr>
  <tr><td>HTML</td><td>Beginner</td></tr>
</table>

th = header cell. td = data cell. tr = row.

Forms

Forms collect information from humans

<form>
  <label for="email">Email</label>
  <input id="email" type="email" required>
  <button type="submit">Join</button>
</form>

Always connect label and input with matching for / id. That is accessibility and usability.

Today forms will not “send” anywhere. That’s OK. Explain action/method will matter when we have a backend. For now, structure is the skill.

<select><option>Student</option></select>
<input type="checkbox"> I agree

Semantic HTML

Choose tags for meaning, not only for boxes

Old habit

<div>Home</div>
<div>Article</div>
<div>Footer</div>

Clearer meaning

<header>Home</header>
<article>...</article>
<footer>...</footer>

Common landmarks: header nav main section article aside footer.

Why semantics matter

Accessibility

Screen readers can jump to nav and main.

SEO

Search engines understand your outline.

Teamwork

Other developers can read your intent.

Is a <div> “wrong”? When is it OK?

It is a generic box. Use it when no semantic tag fits — not as your only tool.

Accessibility basics

HTML is already an accessibility tool — if we use it well

  • Use real headings, not big bold paragraphs.
  • Write useful alt text. Decorative images can use alt="".
  • Never use color alone to mean “error”.
  • Make link text descriptive: “Open my resume”, not “click here”.
  • Give the page a language: <html lang="en">.

Common HTML mistakes

Unclosed tags

The page “kind of works” then breaks later. Validate as you go.

Wrong file paths

img and a href fail silently-looking. Check spelling and folders.

Using tables for layout

We will use CSS for layout on Days 2–3.

Skipping labels on inputs

Placeholder is not a label.

Recap

What we learned

Web model

Browser requests. Server responds. Browser renders.

HTML job

Structure and meaning — not colors.

Document

doctype, html, head, body.

Content tools

Headings, media, lists, tables, forms, semantics.

Common mistakes to avoid tonight

  • Styling with random tags instead of waiting for CSS.
  • Copy-pasting huge templates you do not understand.
  • Broken image paths — always test locally.
  • Multiple h1s or skipped heading levels.

Key takeaways

  1. Websites are files delivered on request.
  2. Frontend is what users see; backend is the kitchen.
  3. HTML describes structure and meaning.
  4. Semantic tags and labels help humans and machines.
  5. Save → refresh → check. That is the developer loop.
